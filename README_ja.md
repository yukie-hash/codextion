## Description
この課題は、「食事する哲学者の問題」を「オフィスのUSBドングル争奪戦」に翻案したもので、デッドロック回避・飢餓状態回避・公平なスケジューリング（FIFO/EDF）・正確なタイマー管理という並行処理の四大テーマを、pthreadのミューテックスと条件変数だけで実装させるものである。

## Instructions

### 必要な環境
- C コンパイラ（`cc`）と `make`
- POSIX スレッド（pthread）が使える環境（Linux / macOS）

### コンパイル
リポジトリのルートで次を実行すると、実行ファイル `codexion` ができる。

```bash
make
```

`-Wall -Wextra -Werror -pthread` 付きでコンパイルされる。

| コマンド | 内容 |
|---|---|
| `make` / `make all` | `codexion` をビルドする |
| `make clean` | オブジェクトファイル（`obj/`）を削除する |
| `make fclean` | `clean` に加えて `codexion` も削除する |
| `make re` | `fclean` してからビルドし直す |

### 実行方法
引数は8つで、すべて必須。

```bash
./codexion number_of_coders time_to_burnout time_to_compile time_to_debug \
           time_to_refactor number_of_compiles_required dongle_cooldown scheduler
```

| 引数 | 単位 | 意味 |
|---|---|---|
| `number_of_coders` | 人 | コーダーの数（＝ドングルの数）。1 以上 |
| `time_to_burnout` | ms | 最後のコンパイル開始（またはシミュレーション開始）からこの時間内に次のコンパイルを始めないと燃え尽きる |
| `time_to_compile` | ms | コンパイルにかかる時間。この間ドングルを2つ持つ |
| `time_to_debug` | ms | デバッグにかかる時間 |
| `time_to_refactor` | ms | リファクタリングにかかる時間 |
| `number_of_compiles_required` | 回 | 全員がこの回数コンパイルしたらシミュレーションが終わる |
| `dongle_cooldown` | ms | ドングルを返してから、再び使えるようになるまでの時間 |
| `scheduler` | — | ドングルを誰に渡すかの規則。`fifo`（要求した順）または `edf`（燃え尽きる期限が近い順） |

数値は 0〜2147483647 の整数のみ受け付ける。負の数・小数・数字以外を含む値・`fifo` / `edf` 以外の scheduler はエラーになり、標準エラー出力に理由と使い方を表示して終了する（終了コード 1）。

### 実行例

```bash
# 誰も燃え尽きず、全員が7回コンパイルして終わる
./codexion 5 800 200 200 200 7 0 fifo

# 期限が短すぎて、誰かが燃え尽きる
./codexion 4 310 200 100 100 5 0 edf

# クールダウンあり
./codexion 4 600 100 100 100 5 50 edf

# コーダー1人（ドングルが1つしかないのでコンパイルできず燃え尽きる）
./codexion 1 800 200 200 200 5 0 fifo
```

### 出力
コーダーの状態が変わるたびに、標準出力に1行ずつ出る。先頭はシミュレーション開始からの経過時間（ms）、次がコーダー番号。

```
0 1 has taken a dongle
0 1 has taken a dongle
0 1 is compiling
0 3 has taken a dongle
0 3 has taken a dongle
0 3 is compiling
200 1 is debugging
...
1204 3 burned out
```

シミュレーションは、誰かが燃え尽きたとき（`burned out` が最後の行になる）か、全員が `number_of_compiles_required` 回コンパイルしたときに終わる。

## Blocking cases handled
### デッドロック防止とコフマンの条件

#### デットロックのシナリオ
- 全員が同じタイミングで左側のドングルだけ確保してしまうと、誰も右側を取れず、円環状にお互いを待ち続けて永遠に止まる。(典型的デットロック)。

#### デットロック回避の方法
- コフマンの4条件（デットロックになりうる条件）のうち、どれかを崩す
  - 相互排他（Mutual Exclusion）資源（データや機器など）を同時に1つの処理しか使えない状態です。他の処理が使うには、終わるまで待つ必要があります。
  - 保持と待機（Hold and Wait）ある資源を自分で持ったまま、別の新しい資源が空くのを待っている状態です。
  - 横取り不可（Non-preemption）ほかの処理がすでに使っている資源を、強制的に奪い取ることができない状態です。持ち主が自分で手放すのを待つしかありません。
  - 循環待ち（Circular Wait）処理同士が輪（円環）のように、お互いの資源の解放を待ち合っている状態です（例：処理Aは処理Bの資源を待ち、処理Bは処理Aの資源を待つ）。  

#### デットロック対応策
  - 取り合いを一元管理する　→　スケジュール管理のため
  - 2つ同時に取れるときだけ実際に取る　→　ドングルを取得する際の分岐でチェック

### 飢餓状態の防止
#### スタベーションとは
- システム全体は動き続けているのに、特定の人だけがいつまでも資源をもらえない状態のこと。
- デッドロックと違って決まった形はなく、「誰を先にするか」のルールの弱点として起きる。なので、自分が選んだルールで何が起きるかを考える必要がある。

#### この課題で起こり得るスタベーション
1. **基本のルール**：ドングルごとに待ち行列を作り、前にいる人から取る（FIFO は要求した順、EDF は期限が近い順）。
2. **問題**：前の人がまだ取れないと、ドングルが空いている後ろの人まで待たされる（先頭ブロッキング）。4人でも1人ずつしかコンパイルできず、間に合うはずの条件でも燃え尽きた。
3. **追い越しを許すと飢餓が起きる**：2 を直すために「前の人が取れないなら追い越してよい」とすると、真ん中の人が困る。コーダーは左右2つのドングルが同時に空いていないと取れないので、両隣が交互に使い続けると、真ん中の人は永遠に取れない。

#### 対応策：期限に間に合うときだけ追い越しを許す（`src/scheduler_rival.c`）
- 前にいる人（R）を追い越してよいのは、次の両方を満たすときだけ。
  1. R が今すぐは取れない
  2. 自分が先に使っても、R の期限に間に合う（`現在時刻 + time_to_compile + dongle_cooldown + 5ms ≦ R の期限`）
- 1 で空いているドングルを無駄にせず、2 で追い越しによって R が燃え尽きることを防ぐ。R の期限が近づくと誰も R を追い越せなくなる。

### クールダウンの処理

#### 求められていること
- ドングルを返してから `dongle_cooldown` ms が経つまで、そのドングルは誰も取れない。

#### 実装
- ドングルごとに「次に使えるようになる時刻」（`dongle_cooldown_until[]`）を持つ。
- 返すときに `現在時刻 + dongle_cooldown` を記録する（`release_dongles`）。
- 取れるのは「空いている」かつ「その時刻を過ぎている」ときだけ（`dongle_ready`）。
- どちらの値も `dongle_mutex` の中で読み書きするので、返した直後の中途半端な状態を他のコーダーが見ることはない。

#### 待ち方
- 取れない理由によって待ち方を変えている（`wait_for_dangles`）。

| 取れない理由 | 待ち方 | 理由 |
|---|---|---|
| 誰かが使用中 | `pthread_cond_wait` | 返すときに `pthread_cond_broadcast` で起こしてもらえる |
| クールダウン中 | `pthread_cond_timedwait`（クールダウンが明ける時刻まで） | クールダウンは時間が経てば明けるだけで、誰も起こしてくれない。`cond_wait` だと寝たままになってしまう |

- 時刻を指定して寝るので、短い間隔で何度も確認する（ポーリング）必要がなく、CPU を無駄に使わない。

### 正確なバーンアウト検出

#### 求められていること
- コーダーとは別のモニタースレッドがバーンアウトを見つけ、シミュレーションを止める。
- `burned out` のログは、実際にバーンアウトした時刻から 10ms 以内に出す。

#### 判定のしかた（`src/monitor.c`）
- モニターは 1ms ごとに全コーダーを確認し、`現在時刻 - 最後のコンパイル開始時刻 > time_to_burnout` の人がいればバーンアウトとする。
- 「最後のコンパイル開始時刻」の初期値はシミュレーション開始時刻にしている。これで「開始から `time_to_burnout` 以内に最初のコンパイルを始めないと燃え尽きる」も同じ式で判定できる。
- 規定回数のコンパイルを終えたコーダーは判定から外す（もうコンパイルする必要がないため）。
- 同じ確認の中で「全員が規定回数を終えたか」も見て、終えていれば正常終了とする。

#### 値を正しく読むための工夫
- 最後のコンパイル開始時刻は、ドングルを取るのと同じ `dongle_mutex` の中で更新する。モニターも同じ mutex の中で読むので、「ドングルは取ったのに時刻はまだ古い」という中途半端な値を見ることはない。

#### 10ms 以内に収まる理由
- 見つかるまでの遅れは、確認間隔の 1ms ＋ `usleep` の寝過ごし（通常 1ms 程度）＋ mutex を待つ時間。mutex の中では配列を1周するだけなので短い。合計しても 10ms に十分収まる。

#### 見つけた後の止め方
1. `dongle_mutex` の中で `stop = 1` にして、`pthread_cond_broadcast` で待っている全員を起こす。
2. `burned out` を出すと同時に、ログを閉じる（`log_closed = 1`）。これ以降、他のコーダーのログは出ない。
3. 各コーダーは、ドングル待ちなら起こされた時点で、作業中なら 5ms ごとの確認（`sleep_ms`）で停止に気づいてループを抜ける。

#### 問題と解決策
通常の`usleep`では、`pthread_cond_broadcast`された時に気づくことができない。そのため、5msごとに確認する設計にしている。

### ログのシリアライズ

#### 求められていること
- 複数のコーダーが同時にログを出しても、1行の中に2つのメッセージが混ざってはいけない。

#### 起こり得る問題
- 何も守らずに複数のスレッドが同時に `printf` すると、出力が途中で混ざることがある（例：`200 1 is debu200 3 has taken a dongle`）。
- 時刻を取ってから出力するまでの間に他のスレッドが割り込むと、タイムスタンプの順番と行の順番が逆になることがある（例：`201` の行の後に `200` の行が出る）。

#### 実装（`src/log.c`）
- ログ専用の mutex（`log_mutex`）を1つ持ち、ログを出すときは必ずこれを取る。
- mutex の中で「経過時間を取る → `printf` で1行出す」までをまとめて行う。
  - 1行を1回の `printf` で出すので、行が混ざらない。
  - 時刻も mutex の中で取るので、行の順番とタイムスタンプの順番が必ずそろう。
- `burned out` を出すときに `log_closed = 1` にする。他のコーダーは `log_closed` を見てからログを出すので、`burned out` の後にログが出ることはない。

## Thread synchronization mechanisms

### 使っている同期の部品

| 部品 | 種類 | 守っているもの |
|---|---|---|
| `dongle_mutex` | `pthread_mutex_t` | ドングルの状態（空き・クールダウン）、待ち行列（ヒープ）、各コーダーの最後のコンパイル開始時刻とコンパイル回数、停止フラグ `stop` |
| `dongle_cond` | `pthread_cond_t` | `dongle_mutex` とセットで使う。「ドングルの状況が変わった」「シミュレーションを止める」をコーダーに知らせる |
| `log_mutex` | `pthread_mutex_t` | 標準出力と、ログを閉じたかどうかのフラグ `log_closed` |

- mutex は2つ、条件変数は1つだけにしている。数が少ないほど、どの mutex で何を守っているかが分かりやすく、取る順番の食い違いによるデッドロックも起きにくい。
- 2つの mutex を同時に握る場所はない。
- スレッドを作る前に決まり、その後変わらない値（引数、開始時刻）は、読むだけなので mutex で守っていない。

### ドングル：取る・返す
- **取るとき**（`take_dongles`）
  1. `dongle_mutex` を取り、左右の待ち行列に自分のチケットを入れる。
  2. 「左右とも空いていて、クールダウンも明けていて、自分の番」になるまで `while` で確認しながら待つ。誰かが使用中なら `pthread_cond_wait`、クールダウン中なら `pthread_cond_timedwait` で寝る。
  3. 取れたら、待ち行列からチケットを消し、2つのドングルを使用中にして、コンパイル開始時刻を記録する。ここまでを1つの mutex の中でまとめて行う。
  4. mutex を離してから `has taken a dongle` を2回出す。
- **返すとき**（`release_dongles`）
  - `dongle_mutex` の中で、ドングルを空きに戻し、クールダウンの終了時刻とコンパイル回数を更新してから、`pthread_cond_broadcast` で待っている全員を起こす。
- **`while` で確認し直す理由**：条件変数は、通知がなくても起きることがある（スプリアスウェイクアップ）。また broadcast で起こされても、自分が取れるとは限らない。
- **`signal` ではなく `broadcast` を使う理由**：誰が取れるかは待ち行列の順番で決まるので、1人だけ起こすと取れない人を起こして終わる可能性がある。

### ログ
- `log_mutex` の中で「経過時間を取る → `printf` で1行出す」を行う。1行が混ざらず、タイムスタンプの順番と行の順番もそろう（詳細は「ログのシリアライズ」）。

### コーダーとモニターのやり取り
- コーダーとモニターは直接やり取りせず、`dongle_mutex` で守られた値を通して情報を渡す。

| 向き | 渡すもの | 書く側 | 読む側 |
|---|---|---|---|
| コーダー → モニター | 最後のコンパイル開始時刻 | コーダーがドングルを取るとき | モニターが 1ms ごとに確認 |
| コーダー → モニター | コンパイル回数 | コーダーがドングルを返すとき | モニターが全員達成したか確認 |
| モニター → コーダー | 停止フラグ `stop` | モニターがバーンアウトか全員達成を見つけたとき | コーダーが待機中・作業中に確認 |
| モニター → コーダー | ログを閉じたかどうか `log_closed` | モニターが `burned out` を出すとき（`log_mutex`） | コーダーがログを出す前に確認 |

- **停止の伝え方**：モニターは `dongle_mutex` の中で `stop = 1` にしてから `pthread_cond_broadcast` する。ドングル待ちで寝ているコーダーは起こされて `stop` を見てループを抜ける。作業中のコーダーは 5ms ごとに `stop` を確認する（`sleep_ms`）。
- **`stop` を `dongle_mutex` で守る理由**：`stop` は条件変数で待つときの条件の一部だから。別の mutex で守ると、コーダーが「`stop` はまだ 0」と確認してから寝るまでの間にモニターが broadcast してしまい、通知を受け取れずに寝続ける（通知の取りこぼし）可能性がある。同じ mutex で守れば、確認と寝る動作の間に割り込まれない。

### 競合状態（データ競合）を防いでいる例
- **ドングルの二重取得**：2人の隣同士が同時に「空いている」と判断して両方取ってしまう問題。確認から取得までを `dongle_mutex` の中でまとめて行うので、片方が取った後でしかもう片方は確認できない。
- **古いコンパイル開始時刻での誤判定**：コーダーがドングルを取ったのに、モニターが更新前の古い時刻を読んでバーンアウトと判定してしまう問題。取得と時刻の更新を同じ mutex の中で行い、モニターも同じ mutex の中で読むので、中途半端な状態は見えない。
- **ログの混ざり**：`log_mutex` で1行ずつ出すので混ざらない。
