
## 概要
複数人が並行して処理を行うことをpthreadで表現する。
限り在るリソース（USBドングル）を複数人で使う場合の競合を解決する。  
また、発生しうるデットロック、スターべションの回避を保証する。

「食事する哲学者の問題」を「オフィスのUSBドングル争奪戦」に翻案したもので、デッドロック回避・飢餓状態回避・公平なスケジューリング（FIFO/EDF）・正確なタイマー管理という並行処理の四大テーマを、pthreadのミューテックスと条件変数だけで実装させる

## 条件(やらなきゃいけないこと)
- 入力条件
    - ドングルの数はコーダーと同じ
    - コーダーは、指定時間内に次のコンパイルをしないと死ぬ
    - コーダーたちは**コンパイル**、**デバッグ**、**リファクタリング**を交互に行う
    - コンパイルに、左右のドングルが必要

- 調停ポリシー
    `fifo`は*先入れ先出し（First In, First Out）*を意味します：ドングルは最初にリクエストしたコーダーに与えられます。`edf`は*最早期限優先（Earliest Deadline First）*を意味し、期限＝`last_compile_start + time_to_burnout`です。

- デッドロック（全員が資源待ちで固まる）の回避
- スタベーション（特定の人だけ資源をもらえない）の回避

- 終了条件
    - 全員に指定回数のコンパイルし終えさせる
    - 燃え尽きる
        - `timestamp_in_ms X burned out`のログをだしてプログラム停止


## 入力
→引数

- プログラムは以下の引数（すべて必須）を取らなければなりません：
  `number_of_coders time_to_burnout time_to_compile time_to_debug time_to_refactor number_of_compiles_required dongle_cooldown scheduler`

  - `number_of_coders`：コーダーの数、およびドングルの数。
  - `time_to_burnout`（ミリ秒）：コーダーが最後のコンパイル開始またはシミュレーション開始から`time_to_burnout`ミリ秒以内にコンパイルを開始しなかった場合、燃え尽きます。
  - `time_to_compile`（ミリ秒）：コーダーがコンパイルするのにかかる時間。この間、2つのドングルを保持していなければなりません。
  - `time_to_debug`（ミリ秒）：コーダーがデバッグに費やす時間。
  - `time_to_refactor`（ミリ秒）：コーダーがリファクタリングに費やす時間。リファクタリングフェーズの完了後、コーダーは直ちにドングルの取得を試み、再びコンパイルを開始します。
  - `number_of_compiles_required`：すべてのコーダーが少なくともこの回数コンパイルを行った場合、シミュレーションは停止します。それ以外の場合は、コーダーが燃え尽きた時点で停止します。
  - `dongle_cooldown`（ミリ秒）：解放された後、ドングルはそのクールダウンが経過するまで**使用不可**です。
  - `scheduler`：複数のコーダーがドングルを要求した際に、どちらに割り当てるかを決めるドングルの調停ポリシー。値は`fifo`または`edf`のいずれか一方でなければなりません。`fifo`は*先入れ先出し（First In, First Out）*を意味します：ドングルは最初にリクエストしたコーダーに与えられます。`edf`は*最早期限優先（Earliest Deadline First）*を意味し、期限＝`last_compile_start + time_to_burnout`です。

- 各コーダーには1から`number_of_coders`までの番号が割り振られます。
- コーダー番号1はコーダー番号`number_of_coders`の隣に座ります。その他のコーダー番号Nは、コーダー番号N-1とN+1の間に座ります。

> **リマインダー：** すべての引数は必須です。負の数、整数でない値、`fifo`または`edf`以外のスケジューラなど、不正な入力は拒否してください。


## 出力
→ログ  

プログラムのログについて：

- コーダーの状態変化はすべて以下の形式でフォーマットしなければなりません：

  - `timestamp_in_ms X has taken a dongle`
  - `timestamp_in_ms X is compiling`
  - `timestamp_in_ms X is debugging`
  - `timestamp_in_ms X is refactoring`
  - `timestamp_in_ms X burned out`

  *`timestamp_in_ms`は現在のタイムスタンプ（ミリ秒）に、`X`はコーダー番号に置き換えてください。*

- 表示される状態メッセージは他のメッセージと混ざってはいけません。
- コーダーが燃え尽きたことを知らせるメッセージは、実際のバーンアウトから10ms以内に表示されなければなりません。

## 各関数について
### ```pthread_t```　スレッドを表す変数の型
### ```pthread_create```　スレッドを作って実行開始
```
pthread_create(&thread, NULL, my_function, &value);
//              ①        ②      ③           ④
```
|番号|	意味|
| ---- | ---- |
|①pthread_t *	|作成したスレッドの情報を格納する変数へのポインタ
|②attr	|スレッドの属性（普通はNULLでデフォルト）
|③関数ポインタ|	このスレッドが実行する関数（戻り値・引数の型が固定）
|④void *	|その関数に渡す引数（何でも渡せるがvoid *にキャストされる）
```
void *関数名(void *arg);
```
**決まりごと**：スレッド関数のシグネチャは固定  
これ以外の形にはできない（戻り値void *、引数1つvoid *）。だから構造体をまとめて渡すのが定番です。

なぜvoid *という型が選ばれているのか：  
void *は「何の型でも指せる汎用ポインタ」です。スレッドに渡したいデータは、コーダーの構造体かもしれないし、将来は別の種類のデータかもしれません。pthreadライブラリは「どんなデータでも渡せる／返せる」ように、あえて型を指定しないvoid *を使うことで汎用性を確保しています。
#### 使用例
```
#include <unistd.h>
#include<pthread.h>
#include<stdio.h>

typedef struct	s_coder
{
    int	id;
	int	compile_count;
}	t_coder;

void	*coder_routine(void	*arg){
	t_coder	*coder = (t_coder *)arg;

	while(1){
		// ドングル取得
		printf("%d is compiling\n", coder->id);
		usleep(200 * 1000); //コンパイル中
		// ドングル返却
		printf("%d is debugging\n",coder ->id);
		usleep(100 * 1000); //デバッグ中
		printf("%d is refactoring\n", coder->id);
		usleep(100 * 1000);
		coder->compile_count++;
	}
	return (NULL);
}

int	main(void){
	pthread_t	threads[3];
	t_coder		coders[3];
	int			i;

	// コーダーを３人作る
	i = 0;
	while(i < 3){
		coders[i].id = i + 1;  //なぜ.?
		coders[i].compile_count = 0;
		pthread_create(&threads[i], NULL, coder_routine, &coders[i]); //構造体を指すポインタを渡す
		i++;
	}

	i = 0;
	while(i < 3){
		pthread_join(threads[i], NULL); //スレッドの終了を待って回収
		i++;
	}
	return (0);
}
```

## 用語
### ミューテックス（Mutex） 
「Mutual Exclusion（相互排他）」を縮めた言葉 
複数のプログラム（スレッドやプロセス）が同じ資源（データやメモリなど）を同時に使わないようにするための排他制御の仕組み。　　
資源のロック、アンロック、待機という動作ができる。
```
#include <pthread.h>

pthread_mutex_t mutex;

pthread_mutex_init(&mutex, NULL);     // ① 初期化
pthread_mutex_lock(&mutex);           // ② ロック（取得）
pthread_mutex_unlock(&mutex);         // ③ アンロック（解放）
pthread_mutex_destroy(&mutex);        // ④ 破棄
```

#### 具体例：共有カウンタを守る
```
typedef struct s_shared
{
    int             counter;
    pthread_mutex_t mutex;
} t_shared;

void *increment(void *arg)
{
    t_shared *s = (t_shared *)arg;
    int i;

    i = 0;
    while (i < 100000)
    {
        pthread_mutex_lock(&s->mutex);    // ← ここから
        s->counter++;                     //   守りたい処理
        pthread_mutex_unlock(&s->mutex);  // ← ここまでが「危険地帯」
        i++;
    }
    return (NULL);
}

int main(void)
{
    t_shared    s;
    pthread_t   t1, t2;

    s.counter = 0;
    pthread_mutex_init(&s.mutex, NULL);

    pthread_create(&t1, NULL, increment, &s);
    pthread_create(&t2, NULL, increment, &s);

    pthread_join(t1, NULL);
    pthread_join(t2, NULL);

    printf("結果: %d\n", s.counter);   // ミューテックスなしだと200000にならないことがある

    pthread_mutex_destroy(&s.mutex);
    return (0);
}
```

### 条件変数（pthread_cond_t）
**「ある条件が満たされるまで、鍵を手放して眠り、誰かに起こしてもらう」**ための仕組みです。ミューテックスだけでは「条件が満たされるまで待つ」という動作を効率よく実現できません（無限ループでチェックし続けると＝CPUを無駄に消費する「ビジーウェイト」になる）。条件変数を使うとスレッドは本当に「眠る」ので無駄がありません。
```
pthread_cond_t cond;

pthread_cond_init(&cond, NULL);              // ① 初期化
pthread_cond_wait(&cond, &mutex);            // ② 待つ（mutexとセットで使う）
pthread_cond_signal(&cond);                  // ③ 1人だけ起こす
pthread_cond_broadcast(&cond);               // ③' 全員起こす
pthread_cond_destroy(&cond);                 // ④ 破棄
```

####  具体例：ドングルの待ち行列
```
typedef struct s_box
{
    int             dongle_available;   // 条件
    pthread_mutex_t mutex;
    pthread_cond_t  cond;
} t_box;

// ドングルを待つ
void take_dongle(t_box *box)
{
    pthread_mutex_lock(&box->mutex);
    while (box->dongle_available == 0)
        pthread_cond_wait(&box->cond, &box->mutex);
    box->dongle_available = 0;         // 使うので0に戻す
    pthread_mutex_unlock(&box->mutex);

    printf("ドングルを取得！\n");
}

// ドングルを返す
void release_dongle(t_box *box)
{
    pthread_mutex_lock(&box->mutex);
    box->dongle_available = 1;
    pthread_cond_broadcast(&box->cond);  // 待っている全員に知らせる
    pthread_mutex_unlock(&box->mutex);
}
```

init          … 条件変数を使えるように準備するだけ（1回だけ）  
wait          … 「条件が満たされるまで眠る」動作。broadcastされるまで、ここで完全に停止する  
broadcast     … 眠っている全員を起こす「きっかけ」を送る  
(whileの再チェック) … 起こされた後、本当に条件が満たされたかを確認する。ここでループを抜けるかどうかが決まる  
### gettimeofday
gettimeofday は、現在時刻を struct timeval に書き込む関数
```
#include <sys/time.h>

struct timeval tv;

if (gettimeofday(&tv, NULL) == -1)
    return (1);
```

第1引数に結果を入れる変数のアドレス、第2引数には通常 NULL を渡す。  
&tv と書くのは、gettimeofday に tv の保存場所を渡して、そこへ結果を書き込んでもらうため。  
成功すると 0 を返し、tv の次のメンバーに時刻が入る。  

| メンバー | 内容 |
|---|---|
| `tv.tv_sec` | 1970年1月1日 00:00:00 UTC からの秒数 |
| `tv.tv_usec` | 1秒未満の部分をマイクロ秒で表した値 |

どちらもミリ秒に揃えるなら、
```tv.tv_sec * 1000 + tv.tv_usec / 1000```
例えば、時刻が「2秒と350000マイクロ秒」なら、変換して足すと時刻全体をミリ秒で表せる。  
1ms = 1,000µs = 1,000,000ns

### ヒープとは
「一番小さい（または大きい）値を、すばやく取り出せる」ように整理して持っておくデータ構造です。

#### 構造：二分木を配列で持つ
ヒープは、次のルールを守る二分木です。
**親のキー ≦ 子のキー（親は必ず子より小さい）**
親子の位置は、計算で分かります。

|求めたいもの	|式
|--|--|
|親	|(i - 1) / 2
|左の子	|2 * i + 1
|右の子	|2 * i + 2

#### 操作
##### push（追加）
1. 配列の末尾に入れる。
2. 親より小さければ、親と入れ替える（sift_up）。
3. これを、親より小さくなくなるまで繰り返す。

##### pop（最小を取り出す）
1. 根（先頭）が最小なので、それを取り出す。
2. 末尾の要素を根に持ってくる。
3. 子のうち小さい方より大きければ、入れ替えて下に沈める（sift_down）。

追加も取り出しも、木の高さ分（約 log n 回）の入れ替えで済みます

キュー ＝ 「受付の行列」という役割  
ヒープ ＝ その行列を、緊急度の高い順に並べておくための整理方法

## デットロック
### デットロック回避の方法
- コフマンの4条件（デットロックになりうる条件）のうち、どれかを崩す
  - 相互排他（Mutual Exclusion）資源（データや機器など）を同時に1つの処理しか使えない状態です。他の処理が使うには、終わるまで待つ必要があります。
  - 保持と待機（Hold and Wait）ある資源を自分で持ったまま、別の新しい資源が空くのを待っている状態です。
  - 横取り不可（Non-preemption）ほかの処理がすでに使っている資源を、強制的に奪い取ることができない状態です。持ち主が自分で手放すのを待つしかありません。
  - 循環待ち（Circular Wait）処理同士が輪（円環）のように、お互いの資源の解放を待ち合っている状態です（例：処理Aは処理Bの資源を待ち、処理Bは処理Aの資源を待つ）。  

### デットロックのシナリオ
- 全員が同じタイミングで左側のドングルだけ確保してしまうと、誰も右側を取れず、円環状にお互いを待ち続けて永遠に止まる。(典型的デットロック)。

### デットロック対応策
  - 取り合いを一元管理する　→　スケジュール管理のため
  - 2つ同時に取れるときだけ実際に取る　→　分岐でチェックできそう
  - ~~コーダーごとに取得順を変える~~　→　知らん、忘れる

## スタベーション
### 起こり得るスタベーション
- FIFOは公平に見えて、実は要求のタイミング次第で特定の人が毎回最後尾になりやすい構造になりがちです。例えば処理時間の関係で、あるコーダーだけ毎回「デバッグ・リファクタリングが早く終わって列に並ぶタイミングが遅い」場合、他の人に先を越され続け、time_to_burnoutに間に合わなくなることがあります。
