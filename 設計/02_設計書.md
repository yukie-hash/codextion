## 1. 設計方針

| 方針 | 内容 | 対応要件 |
|---|---|---|
| P-1 仲介者方式 | ドングルの取得・解放は、**1つの mutex（`dongle_mutex`）で守られた共有テーブル**を通して行う。コーダーが個々のドングルを順番にロックすることはしない | FR-06, FR-09 |
| P-2 All-or-Nothing | 左右2つのドングルは**両方取れるときだけ同時に取る**。片方だけ握って待つことはない | FR-09 |
| P-3 チケット制＋条件付き追い越し | ドングルごとに待ち行列（ヒープ）を持つ。基本は前にいる人が優先。ただし**前の人が今すぐ取れず、自分が先に使ってもその人の期限に間に合うときだけ**追い越してよい（7.6） | FR-08, FR-09 |
| P-4 待機は条件変数 | 待つときは `pthread_cond_wait` / `pthread_cond_timedwait`。ビジーループしない | NFR-07 |
| P-5 終了判定はモニターに集約 | 「誰かが燃え尽きた」「全員達成した」の判定はモニターだけが行う。例外はスレッド作成失敗時の `request_stop` | FR-10, FR-12 |
| P-6 細切れの sleep | 待ち時間は 5ms 単位に分けて寝て、そのたびに停止フラグを見る（`sleep_ms`） | FR-12, D-11 |
| P-7 グローバル禁止 | 全状態を `t_simulation` に集め、`main` のローカル変数として持つ。各スレッドにはポインタで渡す | C-05 |

## 2. システム構成（スレッド構成）

```
                    ┌──────────────────────────────────┐
                    │           main スレッド             │
                    │ parse → init → start_threads      │
                    │   → cleanup（join → destroy → free）│
                    └─────────────────┬────────────────┘
             pthread_create           │         pthread_create
        ┌──────────┬──────────────────┼──────────────────┐
        ▼          ▼                  ▼                  ▼
   ┌────────┐ ┌────────┐         ┌────────┐        ┌──────────┐
   │coder 1 │ │coder 2 │  ...    │coder N │        │ monitor  │
   └───┬────┘ └───┬────┘         └───┬────┘        └────┬─────┘
       │  take / release / sleep_ms  │                  │ 1ms ごとに check
       ▼          ▼                  ▼                  ▼
  ┌──────────────────────────────────────────────────────────┐
  │   共有状態（dongle_mutex で保護）                           │
  │   dongle_free[] / dongle_cooldown_until[]                 │
  │   dongle_queues[]（ヒープ） / next_ticket_number            │
  │   coder.last_compile_start_ms / coder.compile_count       │
  │   stop          ── dongle_cond で待機・通知 ──              │
  └──────────────────────────────────────────────────────────┘
  ┌──────────────────────────────────────────────────────────┐
  │   ログ（log_mutex で保護）  stdout / log_closed              │
  └──────────────────────────────────────────────────────────┘
```

- スレッド数：コーダー N 本 ＋ モニター 1 本 ＋ main。
- mutex は **2つだけ**（`dongle_mutex`、`log_mutex`）。cond は **1つだけ**（`dongle_cond`）。
  - 少ないほどロック順序の問題が起きにくく、説明もしやすい。代わりに並列度は下がるが、本課題の規模では問題にならない。
  - 2つの mutex を同時に握る場所はない（`dongle_mutex` を離してから `log_event` を呼ぶ）。なのでロック順序によるデッドロックは起きない。

## 4. データ設計

### 4.1 構造体（使っているメンバのみ）

```c
typedef enum e_scheduler { scheduler_fifo, scheduler_edf } t_scheduler;

typedef struct s_args          /* 引数。初期化後は読み取り専用 */
{
    long        number_of_coders;
    long        time_to_burnout;
    long        time_to_compile;
    long        time_to_debug;
    long        time_to_refactor;
    long        compiles_required;
    long        dongle_cooldown;
    t_scheduler scheduler_type;
}   t_args;

typedef struct s_coder
{
    int                 id;                    /* 1..N              */
    int                 compile_count;         /* 完了したコンパイル数 */
    long                last_compile_start_ms; /* 絶対時刻(ms)        */
    int                 left_dongle;           /* = id-1            */
    int                 right_dongle;          /* = id % N          */
    struct s_simulation *simulator;
}   t_coder;

typedef struct s_ticket { long key; int coder_id; } t_ticket;

typedef struct s_heap
{
    t_ticket *tickets;
    int       size;
    int       capacity;   /* = QUEUE_CAPACITY (2) */
}   t_heap;

typedef struct s_simulation
{
    t_args          args;
    t_coder         *coders;                 /* [N] */
    pthread_t       *threads;                /* [N] */
    pthread_t       monitor_thread;
    pthread_mutex_t log_mutex;
    pthread_mutex_t dongle_mutex;
    pthread_cond_t  dongle_cond;
    int             *dongle_free;            /* [N] 1=空き */
    long            *dongle_cooldown_until;  /* [N] 絶対時刻(ms) */
    t_heap          *dongle_queues;          /* [N] ドングルごとの待ち行列 */
    long            next_ticket_number;      /* FIFO 用の通し番号 */
    long            start_time_ms;
    int             stop;
    int             log_closed;
    long            created_coders;          /* 作成に成功したコーダースレッド数 */
    int             monitor_started;         /* モニタースレッドを作成できたか */
}   t_simulation;
```

- `created_coders` と `monitor_started` は、スレッド作成が途中で失敗したときに「**作れた分だけ join する**」ために使う（11.2）。

**定数**

| 名前 | 値 | 意味 |
|---|---|---|
| `QUEUE_CAPACITY` | 2 | 1つの待ち行列に入るチケットの最大数（7.2） |
| `MONITOR_INTERVAL_US` | 1000 | モニターの確認間隔（1ms） |
| `SLEEP_SLICE_MS` | 5 | `sleep_ms` で一度に寝る最大時間 |
| `DEADLINE_MARGIN_MS` | 5 | 追い越し判定で、前の人の期限に対して取る余裕（7.6） |

### 4.2 ドングルの番号付け

コーダー i（1始まり）について：

| | 式 | 例（N=4） |
|---|---|---|
| 左ドングル | `i - 1` | coder1→0, coder2→1, coder3→2, coder4→3 |
| 右ドングル | `i % N` | coder1→1, coder2→2, coder3→3, coder4→**0** |

- 隣り合う coder i と coder i+1 はドングル `i` を共有する。coder N と coder 1 はドングル 0 を共有する（円形）。
- N=1 のときは左右とも 0 → `left == right` で「1人モード」を判定できる。

### 4.3 共有変数と保護の対応表（最重要）

**「誰が書き、誰が読み、何で守るか」**を全共有変数について明示する。helgrind で怒られたらまずこの表と照合する。

| 変数 | 書く | 読む | 保護 |
|---|---|---|---|
| `args.*` | main（init時のみ） | 全員 | 不要（スレッド生成前に確定し以後不変） |
| `start_time_ms` | main（init時のみ） | 全員 | 不要（同上） |
| `created_coders`, `monitor_started` | main（スレッド作成時） | main（cleanup） | 不要（main しか触らない） |
| `dongle_free[]` | coder（take/release） | coder | `dongle_mutex` |
| `dongle_cooldown_until[]` | coder（release） | coder | `dongle_mutex` |
| `dongle_queues[]` | coder（enqueue/dequeue） | coder | `dongle_mutex` |
| `next_ticket_number` | coder（enqueue） | coder | `dongle_mutex` |
| `coder.last_compile_start_ms` | 本人（take） | 他のコーダー（追い越し判定）・monitor | `dongle_mutex` |
| `coder.compile_count` | 本人（release） | 本人・monitor | 書き込みと monitor の読み取りは `dongle_mutex`。本人の読み取りは書き手自身なので競合しない |
| `stop` | monitor・main（`request_stop`） | coder | `dongle_mutex` |
| `log_closed` | monitor（log_burnout） | coder（log_event） | `log_mutex` |
| stdout | 全員 | — | `log_mutex` |

> `stop` を `dongle_mutex` で守っているのは、**`pthread_cond_wait` の条件の一部だから**。
> 条件変数で待つときの条件に関わる変数は、その cond と組の mutex で守らないと「通知の取りこぼし（lost wakeup）」が起きる。

## 5. 処理フロー（全体）

```
main
 ├─ parse_args          失敗 → エラーメッセージ + Usage, return 1
 ├─ init_simulation     失敗 → "Error: memory allocation failed", return 1
 │    ├─ 配列確保（coders, threads, dongle_free, cooldown_until）
 │    ├─ ヒープ確保（N 個 × 容量 2）
 │    ├─ mutex / cond 初期化
 │    ├─ start_time_ms = now
 │    └─ 各コーダー: last_compile_start_ms = start_time_ms
 ├─ start_threads
 │    ├─ start_coders   N 本の pthread_create（成功のたびに created_coders++）
 │    └─ pthread_create(monitor)（成功したら monitor_started = 1）
 │    失敗 → "Error: failed to create a thread"
 │          → request_stop（作成済みのスレッドを止める）→ cleanup → return 1
 └─ cleanup_simulation
      ├─ join_threads（作成済みのコーダーだけ → モニター）
      ├─ mutex / cond destroy
      └─ メモリ free
```

- `last_compile_start_ms` の初期値を `start_time_ms` にすることで、
  「シミュレーション開始から `time_to_burnout` 以内に最初のコンパイルを開始しないとバーンアウト」を同じ式で扱える。

## 6. 詳細設計：デッドロックと飢餓の回避

### 6.1 コフマンの4条件とどれを崩すか

デッドロックは次の4つが**全て**成り立つと起きる。1つでも崩せば起きない。

| 条件 | 意味 | 本設計 |
|---|---|---|
| 相互排除 | 資源は同時に1人しか使えない | 成立（ドングルの性質上、崩せない） |
| **保持と待機** | 何かを握ったまま別のものを待つ | **崩す**：All-or-Nothing（P-2）。両方取れるまで何も握らない |
| 横取り不可 | 他人の資源を奪えない | 成立 |
| **循環待ち** | A→B→C→A と待ちが輪になる | **崩す**：チケットに全順序があり、輪ができない（6.2） |

### 6.2 「誰かは必ず進める」ことの説明

- 待っている全コーダーのチケットは **全順序**（キーが違えばキーで、同じならコーダー番号で比較。7.4）を持つ。
- その中で**最小のチケットを持つコーダー X** を考える。X より前にいる人はいないので、`has_rival` は X に対して必ず偽になる（追い越し判定で X が止められることはない）。
- よって X が取れない理由は「自分のドングルが使用中」か「クールダウン中」だけ。
  - 使用中 → 使っている人は有限時間（`time_to_compile`）で解放し broadcast する。
  - クールダウン中 → X は `timedwait` で終了時刻に起きる。
- したがって X は有限時間で取得できる → 全体が止まることはない（**デッドロックしない**）。

### 6.3 飢餓（starvation）しないことの説明

追い越しを許すと「前にいる人がずっと追い越され続ける」危険がある（7.6 の例）。これを次の2段階で防ぐ。

1. **追い越しは期限に間に合う範囲だけ**：C が T を追い越せるのは `now + compile + cooldown + 5ms ≤ T の期限` のときだけ。C が使い終わり、さらにクールダウンが明けるのは T の期限の 5ms 前より早い。つまり**追い越しが原因で T が期限を過ぎることはない**。
2. **期限が近づくと誰も追い越せない**：時間が経つほど `now` が増えるので、判定は厳しくなる一方になる。T の期限が `compile + cooldown + 5ms` 以内に迫ると、T の行列では誰も T を追い越せない。T は今の使用者が解放した時点で取れる。

- **FIFO**：チケット番号は単調増加なので、後から来た人は前に割り込めない（追い越しは上の条件付きのみ）。
- **EDF**：キーは要求時点の期限で、待っている間は変わらない。後から来る人の期限は「その人の直前のコンパイル開始 + burnout」なので、いずれ自分が最小になる。

## 7. 詳細設計：スケジューラとヒープ

### 7.1 チケット

| scheduler | `key` | タイブレーク |
|---|---|---|
| `fifo` | `next_ticket_number`（要求ごとに +1） | 不要（キーが重複しない） |
| `edf` | `last_compile_start_ms + time_to_burnout` | `coder_id` が小さい方（D-04, 7.4） |

- 1回の要求で**同じチケットを左右2つの行列に入れる**。

### 7.2 ヒープ容量を 2 にできる理由

- 1つのドングルを使う可能性があるのは、その両隣の**2人だけ**。
- 1人が同時に出せる要求は1つだけ（取得するまで次の要求をしない）。
- よって1つの行列に同時に入るチケットは最大2枚 → `QUEUE_CAPACITY = 2` で足りる。

### 7.3 ヒープ操作

最小ヒープ（配列表現、根が最小）。親 `(i-1)/2`、子 `2i+1`, `2i+2`。

| 操作 | 内容 | 計算量 |
|---|---|---|
| `heap_push` | 末尾に追加 → `sift_up`（親より先に来る間入れ替え） | O(log n) |
| `heap_remove` | 指定コーダーのチケットを探し、末尾で上書き → `sift_up` と `sift_down` | O(n)（探索）※n ≤ 2 |

- 比較関数 `ticket_comes_first(a, b)` が FIFO / EDF 共通の順序を決める。scheduler による違いは**キーの作り方だけ**に閉じ込める。
- 追い越しがあるので、取得した人が先頭とは限らない。そのため取り出しは「先頭を消す（pop）」ではなく「**自分のチケットを消す（remove）**」にしている。

### 7.4 タイブレーク規則（D-04）

`ticket_comes_first(a, b)` は「チケット a は b より先に処理されるべきか」を返す。

```
1. key が違う   → key が小さい方が先
2. key が同じ   → coder_id が小さい方が先
```

| 項目 | 内容 |
|---|---|
| 必要になる場面 | EDF で期限が同じ ms になったとき。特に**開始直後は全員の `last_compile_start_ms` が `start_time_ms` なので、全員の期限が同じ**になる |
| FIFO での扱い | `next_ticket_number` は重複しないので、2. は実際には使われない。ただし比較関数は共通なので、同じ規則がそのまま適用される |
| この規則にした理由 | ① 課題が「完全に決定論的な EDF」のためにタイブレークを要求している。② `coder_id` は全員で異なるので、どの2枚のチケットも必ず順序が決まる（**全順序**）。これが 6.2 の「最小のチケットを持つ人が必ず存在する」という説明の前提になる。③ 説明が簡単 |
| 採らなかった案 | 要求到着順（チケット番号）で決める：決定論的にならない（スレッドの実行順に依存する）。ランダム：決定論的でない |
| 副作用 | 開始直後は番号の小さいコーダーが有利になる。ただし1回コンパイルすれば期限が更新されて順位が入れ替わるので、継続的な不公平にはならない |

### 7.5 取得判定

```
can_take(C) =
       dongle_ready(left)  && dongle_ready(right)       # 自分のドングルが空いていてクールダウンも明けている
    && is_my_turn(C)

is_my_turn(C) =
       !has_rival(左の行列, C のチケット)
    && !has_rival(右の行列, C のチケット)

has_rival(行列, mine) = 行列の中に次を満たす人 R がいる
       R のチケットが mine より先（ticket_comes_first）
    && rival_goes_first(R)

rival_goes_first(R) =
       R の左右のドングルが今すぐ使える                    # R がすぐ取れるなら R が先
    || now + compile + cooldown + DEADLINE_MARGIN_MS
         > R.last_compile_start + burnout                 # 自分が先に使うと R が期限に間に合わない
```

### 7.6 先頭ブロッキングと追い越し規則（D-12）

**問題：先頭ブロッキング**

旧設計では「左右**両方の行列で先頭**のときだけ取れる」としていた。4人のとき、t=0 の待ち行列はこうなる。

| ドングル | 待ち行列（先頭→） |
|---|---|
| 0 | 1, 4 |
| 1 | 1, 2 |
| 2 | **2**, 3 |
| 3 | 3, 4 |

3番はドングル2・3が空いているのに、ドングル2の先頭が2番なので取れない。その2番も1番待ちで動けない。結果として **1 → 2 → 3 → 4 の待ちの鎖**ができ、1人ずつしかコンパイルできなかった。実現可能なはずの `4 410 200 100 100` でバーンアウトしていた。

**解決：条件付きの追い越し**

前の人 R を追い越してよいのは、次の**両方**を満たすときだけとする。

1. R が今すぐは取れない（R のドングルのどちらかが使用中かクールダウン中）
2. 自分が先に使っても、R の期限に間に合う（`now + compile + cooldown + 5ms ≤ R の期限`）

上の例では、3番は2番を追い越せる。2番は1番が使い終わる 200ms まで取れないし、3番が 0〜200ms に使っても2番の期限（`burnout`）には間に合うからだ。これで1番と3番が同時にコンパイルできる。

**なぜ条件 2 が必要か（道路の横断）**

```
時間 →      0    100   200   300   400   500
ドングル1   [1番使用中 ]      [1番使用中 ]
ドングル2         [3番使用中 ]      [3番使用中 ]
2番が両方取れる? ✗   ✗    ✗    ✗    ✗    ✗
```

条件 1 だけだと、真ん中の2番は「今すぐ取れない」状態が続き、両隣に追い越され続けて飢餓になる。条件 2 があると、2番の期限が近づいた時点で誰も追い越せなくなる。

**設計上のポイント**

| 項目 | 内容 |
|---|---|
| 期限は scheduler に関係なく使う | 追い越し判定の「R の期限」は FIFO でも `last_compile_start + burnout`。並び順は scheduler で決め、追い越しの安全確認は期限で行う |
| `DEADLINE_MARGIN_MS = 5` の理由 | `sleep_ms` の寝過ごしやログ待ちで、解放が数 ms 遅れることがある。その分の余裕 |
| `compile + cooldown` の理由 | 自分がドングルを握るのは compile の間だけ。その後クールダウンが明けるまで R は取れない |
| 通知の取りこぼしがない理由 | 判定は時間とともに**厳しくなる一方**（`now` が増えるので「追い越し可」→「不可」にしか変わらない）。「不可」→「可」に変わるのは R が取得するか、誰かが解放したときだけで、解放時には broadcast がある。なので `cond_wait` で寝たまま起きられない人は出ない |
| ロック | `has_rival` は `take_dongles` の中で `dongle_mutex` を握ったまま呼ばれる。R の `last_compile_start_ms` やドングル配列を読んでも競合しない |

## 8. 詳細設計：コーダー

### 8.1 状態遷移

```
            ┌──────────────────────────────────────────────┐
            ▼                                              │
     ┌─────────────┐  両方取得   ┌───────────┐  time_to_compile  ┌───────────┐
 ──▶ │ WAITING     │ ─────────▶ │ COMPILING │ ────────────────▶ │ DEBUGGING │
     │ (行列で待機) │            └───────────┘   解放+broadcast   └─────┬─────┘
     └──────┬──────┘                                               │ time_to_debug
            │ stop                                                  ▼
            ▼                                               ┌─────────────┐
       ┌────────┐ ◀── stop / 規定回数達成 ──────────────────  │ REFACTORING │
       │  END   │                                            └─────────────┘
       └────────┘                                         time_to_refactor 後 WAITING へ
```

- COMPILING / DEBUGGING / REFACTORING の途中でも、`sleep_ms` が停止を検知すると END に抜ける。

### 8.2 ループ

```
coder_routine:
    if left == right:  lone_coder(); return
    while (!is_stopped() && compile_count < compiles_required):
        if (!do_compile() || !do_debug() || !do_refactor())
            return                            # 待機中か sleep 中に stop された

do_compile:   take_dongles → log "is compiling" → sleep_ms(compile) → release_dongles
do_debug:     log "is debugging"    → sleep_ms(debug)
do_refactor:  log "is refactoring"  → sleep_ms(refactor)
```

- `do_compile` は `sleep_ms` が停止で中断されても、必ず `release_dongles` してから戻る（ドングルを握ったまま終わらない）。

### 8.3 `take_dongles` のシーケンス

```
coder                    dongle_mutex 内                      他のコーダー
  │ lock ───────────────▶│
  │                      │ enqueue（左右の行列にチケット）
  │                      │ while (!stop && !can_take):
  │                      │     自分のドングルにクールダウン中のものがある?
  │                      │       yes → timedwait(クールダウン終了時刻)
  │                      │       no  → cond_wait          ◀── release の broadcast
  │                      │ if stop: unlock, return 0
  │                      │ dequeue（左右の行列から自分のチケットを remove）
  │                      │ dongle_free[left/right] = 0
  │                      │ last_compile_start_ms = now
  │ unlock ◀─────────────│
  │ log "has taken a dongle" × 2
```

- `while` で条件を再チェックする理由：**スプリアスウェイクアップ**（通知がなくても起きることがある）と、broadcast で起きても自分の番とは限らないため。
- `last_compile_start_ms` の更新は取得と同じロック内で行う。モニターが「取得したのにまだ古い時刻」を見ることがない。

### 8.4 `release_dongles`

```
lock dongle_mutex
    dongle_free[left/right] = 1
    cooldown_until[left/right] = now + dongle_cooldown
    compile_count++
    broadcast(dongle_cond)       # 待っている全員に「状況が変わった」と知らせる
unlock
```

- `signal` ではなく `broadcast` を使う理由：誰が取れるかは行列と追い越し判定次第で、signal だと取れない人を起こして終わる可能性がある。

### 8.5 `sleep_ms`（D-11）

```
sleep_ms(ms):
    end = now + ms
    while (残り > 0 && !is_stopped()):
        usleep(min(残り, 5ms))
        残り = end - now          # 寝過ごしても終了時刻基準で補正される
    return 残り <= 0              # 最後まで寝られたら 1、停止で中断されたら 0
```

| 効果 | 説明 |
|---|---|
| 停止に素早く反応 | バーンアウト後、最大でも約 5ms でスレッドが抜ける |
| 時間のずれが溜まらない | 毎回「終了時刻 − 今」で残りを計算するので、`usleep` の寝過ごしが累積しない |
| 代償 | 5ms ごとに `is_stopped` が `dongle_mutex` を取りに行く。200人なら毎秒 4 万回のロックになり、ドングル待ちの人と同じロックを奪い合う（12.1） |

### 8.6 1人モード（N=1）

- ドングルが1つしかなくコンパイル不可能（D-05）。
- 「has taken a dongle」を1回出し、`stop` が立つまで `cond_wait` で待つ。モニターがバーンアウトを検出し `stop` + broadcast で起こす。

## 9. 詳細設計：モニター

```
monitor_routine:
    loop:
        lock dongle_mutex
            id = 最初に見つかった「未達成 かつ now - last_compile_start > burnout」のコーダー
            if id == 0 and 全員達成: id = -1
            if id != 0: stop = 1; broadcast
        unlock
        if id != 0: break
        usleep(MONITOR_INTERVAL_US)   # 1ms
    if id > 0: log_burnout(id)        # log_closed = 1 にして以後のログを止める
```

- **10ms 要件の見積もり**：検出遅れ ≤ ポーリング間隔 1ms ＋ usleep の寝過ごし（通常 〜1ms 程度）＋ ロック待ち。ロック内の処理は配列走査のみで短い → 10ms に十分収まる。
- ログを `log_burnout` で閉じるので、`stop` を立ててからコーダーが抜けるまでの間に出たログが `burned out` の**後ろ**に来ることはない。

## 10. 詳細設計：ログ

```
log_event(id, msg):
    lock log_mutex
        if !log_closed: printf("%ld %d %s\n", elapsed, id, msg)
    unlock
```

- タイムスタンプは**ロック内で取得**する。ロック外で取ると、時刻の順と出力の順が逆転しうる。
- `printf` 1回で1行を出すので、行が混ざらない。
- ログは「状態が変わった後」に出るので、少し遅れることがある。例えば `is debugging` は解放した後に `log_mutex` を待ってから出る。200人規模では 1〜数 ms 遅れ、隣の人の `is compiling` が先に出ることがある。テストはこの遅れを考慮している（13章）。

## 11. 終了処理・エラー処理

### 11.1 正常終了の順序

1. モニターが `stop = 1` + `broadcast`
2. `cond_wait` 中のコーダーは起きて `stop` を見て `take_dongles` から 0 を返す
3. compile / debug / refactor 中のコーダーは、`sleep_ms` が約 5ms 以内に停止を検知して抜ける（compile 中ならドングルを解放してから）
4. main が作成済みのコーダー → モニターの順に join
5. mutex / cond を destroy（**全スレッド join 後**。使用中に destroy すると未定義動作）
6. メモリを free

### 11.2 エラー時の後始末

| 失敗箇所 | 後始末 | 実装状況 |
|---|---|---|
| `allocate_arrays` | それまでに確保した配列を free | 済 |
| `allocate_dongles` | coders, threads を free | 済 |
| `init_dongle_queues` | 確保済みのヒープと配列を free | 済 |
| `get_current_time_ms`（init 内） | 確保済みのメモリ・ヒープを free、mutex を destroy | **未**（12章 #6） |
| `pthread_create`（k 本目のコーダー、またはモニター） | `request_stop`（stop = 1 + broadcast）→ `created_coders` 本だけ join、モニターは `monitor_started` のときだけ join → destroy / free | 済。ただし2つの変数が初期化されていない（12章 #14） |

### 12.3 設計上の検討課題（バグではない）

- **`sleep_ms` のロック競合**：5ms ごとに `dongle_mutex` を取るので、人数が多いとドングル待ちの人とロックを奪い合う。気になるなら `stop` だけを別の mutex（例：`stop_mutex`）で守る案がある。ただし `stop` は `cond_wait` の条件でもあるので、待機側では `dongle_mutex` で読む必要が残る（4.3 の注意）。今は 200人でもテストが通るので、現状維持。
- **`DEADLINE_MARGIN_MS` の値**：5ms は経験的な値。小さすぎると寝過ごしで期限を割り、大きすぎると追い越しが減って並列性が落ちる。評価で聞かれたら、この両面を説明できるようにする。
